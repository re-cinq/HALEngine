# Conversation List

| Field  | Value                             |
| ------ | --------------------------------- |
| Issue  | re-cinq/HALEngine#143, #144, #145 |
| Status | Shipped                           |

Resume gets a client back into one conversation: the id it names, or the user's most recently active one. Neither tells it which conversations exist, and every other member of `SessionStore` answers about a session the caller can already name, so a consumer wanting to offer a conversation list had to query the collection behind the engine's back, against a document shape and a key the engine owns. `listFor` answers the list instead, as summaries rather than sessions. **GDPR.** A summary is personal data — that a user held a conversation, and when — so it carries no conversation content, it is filtered to one user by the query rather than in application code afterwards, and the retention bound stays the consumer's, through the store's `maxAgeMs` and erasure methods and re-cinq/HALEngine#41. A row of a session id, two timestamps and a count still makes a user pick their own history by date arithmetic, and the engine has no title to offer, because nothing needed one while the only way back into a conversation was an id the client already held; a generated one would be a provider call per conversation on a path that makes none, and a cost the engine would be spending on the consumer's behalf. What it offers instead is the conversation's own opening question, derived on the way out rather than stored: unlike `entryCount` it comes from an entry that never changes once written and costs one element to read, so the user's words are not copied into a second field to be erased separately. **GDPR.** That preview is conversation content, and so personal data of a kind a summary otherwise never carries — in a support deployment an opening question can hold a booking reference, an order number or another person's name, which that deployment's own data-flow record has to account for — so both of its switches default to off, a deployer turning them on extends what a client renders under their own lawful basis, and retention stays bounded by the same `maxAgeMs`, erasure methods and re-cinq/HALEngine#41. One consequence of reading the stored entry rather than a copy: a `beforeUserInput` hook's return value is written back to that same entry, so a deployment that enriches a user message before answering it labels its conversations with the enriched text rather than with what the user typed. That is a caveat and not a seam — titling a conversation through that hook would overwrite the user's own words in the history the model reads and a resume replays — and a stored title a consumer writes is tracked separately in re-cinq/HALEngine#155.

## The summary

- A summary is `sessionId`, `createdAt`, `updatedAt` and `entryCount` — a label, below, being the only field a caller can add — and nothing else: neither the conversation's entries nor its credentials, so a list can never hand over either, even for a session created with credentials ([validated by: carries only its four fields, so a list can never hand over a conversation or a credential](../../src/infrastructure/stores/sessionStoreListSignature.test.ts#L22)).
- `listFor` is optional, like `latestFor` and `lookup` before it: a store written against the five original members still satisfies the interface, and both shipped stores implement it ([validated by: leaves a store with only the five original members satisfying the interface beside both shipped ones](../../src/infrastructure/stores/sessionStoreListSignature.test.ts#L11)).

## The order a list answers in

- Summaries come back most recent activity first ([validated by: answers newest activity first, headed by the very session latestFor returns](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L27)).
- The first summary is the session `latestFor` returns, because both read the same activity ([validated by: answers newest activity first, headed by the very session latestFor returns](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L27)).
- The order is total rather than merely sorted: two conversations last active in the same millisecond are ordered by session id, the larger first, which is what lets a page resume without dropping one of them ([validated by: keeps a conversation tied on activity rather than dropping it across a page boundary](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L196)).
- In `InMemorySessionStore` that tie-break is the list's alone: `latestFor` breaks the same tie by creation order, so for two tied conversations the head of the list and the session a resume rejoins can differ ([validated by: breaks a tie on activity by session id, where latestFor takes the session created later](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L42)).
- `MongoSessionStore` answers in order of `updatedAt`, which each `save` moves forward, and its first summary is the session its own `latestFor` returns ([validated by: answers the user's conversations newest saved first, headed by the one latestFor returns](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L65)).
- It breaks a tie by `_id` in both members, so there the head of the list is the session a resume rejoins even when every conversation shares an `updatedAt` ([validated by: heads the list with the session latestFor returns even when every conversation shares an updatedAt](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L317)).

## What a summary reports

- `InMemorySessionStore` reports the moment `create` was called, the newest entry time as the activity, and the conversation's entry count ([validated by: reports a creation time, the newest activity and the entry count of each conversation](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L53)).
- `MongoSessionStore` reports the document's `createdAt`, the `updatedAt` its last save wrote, and the counter written beside the entries ([validated by: reports the creation time, the last save and the entry count of each conversation](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L83)).
- That counter is what a save writes, so a list never reads a conversation to count one ([validated by: counts a conversation from the field a save writes beside the entries](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L129)).
- A document written before the counter existed reads as a conversation of no entries rather than failing the list, which is what the backlog documented in `docs/session-stores.md` is for ([validated by: reads a conversation saved before the counter existed as one of no entries, rather than failing](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L113)).

## A label for a row

- `preview` is asked for and never volunteered: `SessionListOptions.preview` defaults to `false`, and a summary from a list that did not ask carries no `preview` key at all rather than an empty one ([validated by: carries no preview key for a list that did not ask for one, nor for an explicit preview of false](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L141)).
- Asked for, a summary carries the text of the conversation's first entry, and only where that entry is the user's, trimmed and with every run of internal whitespace replaced by one ASCII space — a run of one included, so a non-breaking or ideographic space becomes an ordinary one — and a question typed across several lines reads as one line in a list ([validated by: is the opening question, trimmed and with its internal runs of whitespace collapsed](../../src/infrastructure/stores/sessionPreview.test.ts#L13)).
- It is a label rather than an excerpt: at most 120 code points, cut with no ellipsis added, because how to mark a cut is the client's decision and a page of fifty rows should carry a few kilobytes rather than a transcript ([validated by: is cut to a hundred and twenty code points, with no ellipsis of its own](../../src/infrastructure/stores/sessionPreview.test.ts#L17)).
- The cut counts code points rather than UTF-16 units, so a question ending in an emoji is never cut through the middle of a surrogate pair and shipped as a lone half ([validated by: is cut by code point rather than by UTF-16 unit, so a pair is never halved](../../src/infrastructure/stores/sessionPreview.test.ts#L23)).
- A cut may still land inside a grapheme cluster, so a combining mark can be dropped from the character it sits on; a zero-width joiner the cut stranded is removed, along with a stranded space, because neither is visible and no client could style away a cut it did not make ([validated by: drops a joiner the cut left with nothing to join, since it is invisible in what a client renders](../../src/infrastructure/stores/sessionPreview.test.ts#L62)).
- Only a `UserEntry` is ever read: a conversation opening with an entry the model wrote, an assistant, thinking or tool entry alike, is labelled with nothing rather than with that entry's words ([validated by: is absent for a conversation that opens with an entry the model wrote, whatever that entry says](../../src/infrastructure/stores/sessionPreview.test.ts#L29)).
- That rule is what keeps a list from showing text the live stream withheld: a tool that suppresses a response leaves the assistant entry in the session for the model's history, and a label reading it would put on screen the one text the engine deliberately did not send ([validated by: labels a conversation from the user's question even where a tool suppressed the answer to it](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L161)).
- A conversation with no entries at all, and one whose entries are all model-authored, carry no label rather than an empty one ([validated by: labels nothing for a conversation with no entries, nor for one opening with a model-authored entry](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L180)).
- A question of whitespace alone is no label either, since `''` is a row a client would render blank and absent is what says so honestly ([validated by: is absent for a conversation with no entry at all, and for one asked in whitespace alone](../../src/infrastructure/stores/sessionPreview.test.ts#L42)).
- A label is the one field a summary carries beyond its four, and it brings no others: still no entries and no credentials, even for a session created with them ([validated by: carries one field more for a label, and still neither the conversation nor a credential](../../src/infrastructure/stores/sessionStoreListSignature.test.ts#L41)).
- `InMemorySessionStore` reads the first entry off the session it holds, and only for the rows of the page it is answering with ([validated by: labels a conversation with its opening question when one is asked for](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L151)).
- `MongoSessionStore` adds `{entries: {$slice: 1}}` to its projection, and asks for no entry at all when no label was wanted, so the cheap path stays as cheap as it was ([validated by: asks the database for the first entry alone when a label is wanted, and for no entry otherwise](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L157)).
- That slice is what the database actually returns, so a labelled read of a conversation of many entries carries one of them out and a list still never takes a conversation out of the database ([validated by: carries one entry out of the database for a label, never the conversation behind it](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L201)).
- A stored entries field that is absent, `null` or not an array at all is labelled with nothing rather than failing the list: MongoDB applies `$slice` only to an array and hands back any other value untouched, so a document migrated from another schema reaches the mapper intact and a hand-written adapter cannot turn a label into an error ([validated by: survives a real database answering a slice of a field that is not an array, as a migrated document would](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L217)).
- The same holds for an adapter of a consumer's own answering the shapes a real database answers with ([validated by: labels nothing where a stored entries field is absent, null or not an array, rather than failing](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L238)).
- An entry whose text is missing, `null` or not a string is labelled with nothing for the same reason, since an entry that can lie about its `role` can lie about its `content`, and one bad row must not fail the page ([validated by: is absent for a stored entry whose text is missing or is not text, rather than failing the whole list](../../src/infrastructure/stores/sessionPreview.test.ts#L46)).
- The label is derived from that sliced entry ([validated by: labels a conversation with the opening question the slice returned](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L170)).
- Where the sliced entry is not the user's, the row is labelled with nothing rather than wrongly: the protocol invariant puts a `UserEntry` ahead of an `AssistantEntry`, so in a conversation holding a user entry at all it is element zero, and a deployment that writes an entry of its own ahead of the user's gets no labels rather than wrong ones ([validated by: labels nothing when the entry the slice returned is not the user's, rather than labelling it wrongly](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L184)).
- The limit and the cursor apply to a labelled list exactly as to a plain one, in both stores, so asking for labels never widens a page nor reorders one — and a limit lost on the labelled path would be read by MongoDB as no limit at all ([validated by: window a labelled list the same way, so asking for labels widens no page and reorders none](../../src/infrastructure/stores/storeListAgreement.test.ts#L96)).
- An explicit `preview: false` is the shape the transport sends on the cheap path, and both stores read it as asking for no label: no key on the row, and no entry in the Mongo projection ([validated by: asks for no entry and labels nothing for an explicit preview of false, which is what the transport sends](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L255)).
- `InMemorySessionStore` reads an absent option and an explicit `false` alike ([validated by: carries no preview key for a list that did not ask for one, nor for an explicit preview of false](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L141)).
- A plain list carries no label even from a collection that answered with the entries anyway, so an adapter ignoring the projection cannot volunteer one ([validated by: labels nothing on a plain list even where the collection answered with the entries anyway](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L271)).
- Both shipped stores derive the same label from the same conversation, and refuse a model-authored opening alike, so a consumer swapping one for the other sees the same labels ([validated by: label a conversation with the same opening question, and refuse a model-authored opening alike](../../src/infrastructure/stores/storeListAgreement.test.ts#L62)).

## Whose conversations

- A list holds only the asking user's conversations: another user's never appear, and a user with none gets an empty list ([validated by: omits a conversation that aged out and another user's, and answers nothing for a user with none](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L65)).
- `InMemorySessionStore` omits a conversation that has aged out, as `latestFor` does ([validated by: omits a conversation that aged out and another user's, and answers nothing for a user with none](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L65)).
- `MongoSessionStore` filters on the user in the database, sorts on `{updatedAt: -1, _id: -1}` — the `{userId: 1, updatedAt: -1}` index `latestFor` already needs serves its leading keys — and asks for a projection that leaves the entries behind, one sliced entry excepted where a label was asked for ([validated by: asks the database to filter on the user, sort on the index with the id behind it, and never for the entries](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L138)).
- It answers from that projection alone, so a collection that never returns an entry still lists conversations — the conversation does not leave the database to be listed ([validated by: answers from a projection alone, so a collection that never returns entries still lists conversations](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L337)).

## Paging

- `limit` takes that many of the newest, and `before` resumes after a row, so a client pages by passing back the last summary it saw — `SessionCursor` is `updatedAt` and `sessionId`, which a `SessionSummary` already satisfies ([validated by: pages down the same order: a limit takes the newest, and before takes what is older than it](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L78)).
- Paging walks every conversation exactly once even when all of them share an activity time, because the cursor carries the session id the order breaks ties on: a tie cannot fall between two pages and be skipped ([validated by: keeps a conversation tied on activity rather than dropping it across a page boundary](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L196)).
- `MongoSessionStore` pages the same way ([validated by: pages with before and a limit, down the same newest-first order](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L96)).
- It walks a tie exactly once too, through the same cursor ([validated by: keeps a conversation tied on updatedAt rather than dropping it across a page boundary](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L283)).
- A list is at most 200 summaries however many are asked for, and 50 when none is asked for, so no caller can ask for an unbounded page ([validated by: answers at most two hundred conversations however many are asked for, and fifty when none is](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L94)).
- That limit bounds the rows answered, not the rows the database reads to answer them: on `MongoSessionStore` the work is bounded by the `{userId: 1, updatedAt: -1, _id: -1}` index `docs/session-stores.md` prescribes, and under the two-key form Mongo sorts the user's whole history before applying the limit ([validated by: needs the three-key index to answer without sorting the whole history, which the two-key form does not](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L348)).
- A fractional limit is floored rather than refused, since a slip in a limit is not a reason to deny a user their history ([validated by: floors a fractional limit, and reads a negative or unusable one as none given rather than as nothing](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L104)).
- A negative limit, and one that is not a usable number, are read as no limit given at all rather than as a limit of none: handing a user an empty history for a typo is the worse reading ([validated by: floors a fractional limit, and reads a negative or unusable one as none given rather than as nothing](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L104)).
- Only a limit of exactly `0` answers no conversations ([validated by: answers nothing only for a limit of exactly none](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L116)).
- `MongoSessionStore` answers a limit of `0` without querying, because MongoDB reads `limit: 0` as no limit at all and would otherwise answer with every conversation the filter matches ([validated by: answers a limit of none without asking the database, which reads a limit of zero as no limit at all](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L299)).

## The two shipped stores answer one order

- `InMemorySessionStore` and `MongoSessionStore` list the same conversations in the same order, so a consumer swapping one for the other sees the same conversation list ([validated by: answer the same order for conversations whose activity differs](../../src/infrastructure/stores/storeListAgreement.test.ts#L44)).
- They break a tie on activity the same way, by session id ([validated by: break a tie on activity the same way, by session id](../../src/infrastructure/stores/storeListAgreement.test.ts#L53)).
- They page identically through the documented call, `listFor(userId, {limit, before: rows.at(-1)})`, a page at a time until a page comes back empty ([validated by: page the same way through the documented call, two rows at a time from the last row seen](../../src/infrastructure/stores/storeListAgreement.test.ts#L115)).

## Asking for the list over the socket

- Serving a list is its own switch, `transport.history`, and not part of `transport.resume`: resume on with history off still refuses the frame. Rejoining hands a client back a conversation it was already in, while a list tells it what else the user has, and a deployer who agreed to the first did not thereby agree to the second ([validated by: refuses the frame with resume on but history off, since one switch is not the other](../../src/transport/conversationList.test.ts#L314)).
- With `history.enabled`, a `list_conversations` frame is answered with exactly one `conversation_list` and nothing else — no frame belonging to a turn, no `stream_end` — carrying the user's conversations newest activity first, each `createdAt` and `updatedAt` an ISO string rather than a `Date`, which is what survives the wire ([validated by: answers the user's conversations newest first, with both times as ISO strings](../../src/transport/conversationList.test.ts#L100)).
- The frame is built from four fields and nothing else — a label, below, being the only field a deployment can add — so a store answering whole sessions, entries, credentials and another user's id among them, still puts only a summary on the wire ([validated by: sends only the four summary fields, so a store answering whole sessions leaks neither entries nor credentials](../../src/transport/conversationList.test.ts#L265)).
- A row's times go on the wire as ISO strings whatever the store answered with, a `Date`, a string or an epoch number, so a store written against the shape the wire shows is not a failed read ([validated by: puts a time on the wire as an ISO string whatever shape the store answered with](../../src/transport/conversationList.test.ts#L212)).
- The list is the connecting user's, taken from the connection: a frame carrying a `userId` of somebody else is answered with the caller's own conversations, and the store is asked for the caller's id ([validated by: answers the connecting user's own conversations even when the frame names another user](../../src/transport/conversationList.test.ts#L126)).
- `limit` and `before` reach the store as the frame sent them, so a client pages the socket the way a consumer pages the store ([validated by: carries a limit and a cursor through to the store as the frame sent them](../../src/transport/conversationList.test.ts#L200)).
- The conversation the connection is itself in is listed like any other, so a fresh connect sees a row of its own holding no entries ([validated by: lists the conversation the connection is in, like any other, holding no entries yet](../../src/transport/conversationList.test.ts#L325)).
- A label on the wire is the deployer's own second switch, `transport.history.preview`: with history on and preview off the store is not asked for one, and a client naming `preview` in the frame is not served one, because the validator rebuilds the frame from the fields it defines ([validated by: asks the store for a preview only where this deployment allows one, never because a client asked](../../src/transport/conversationList.test.ts#L188)).
- With `history: {enabled: true, preview: true}` each row carries its conversation's opening question ([validated by: labels each conversation with its opening question where the deployer turned previews on](../../src/transport/conversationList.test.ts#L179)).
- The transport re-applies the collapse and the cut to whatever a store answered, as it rebuilds the times, so the bound the protocol documents holds for a consumer's own store and a non-string reaches no client ([validated by: holds a store answering an over-long or non-text preview to the field the protocol documents](../../src/transport/conversationList.test.ts#L154)).
- A stranded space goes with the stranded joiner, so a label never ends in the middle of a gap between words ([validated by: tidies a space the cut stranded at the end, so the label never ends mid-gap](../../src/infrastructure/stores/sessionPreview.test.ts#L100)).
- Whether a cut landed is decided by what the text held rather than by the label's length, so a question that ends exactly at the bound keeps its last character ([validated by: counts a cut by what the text held, so a label at the bound that was never cut keeps its last character](../../src/infrastructure/stores/sessionPreview.test.ts#L68)).
- A tidy-up applies only where a cut actually landed: text the cut never reached ends where the user ended it, joiner included, since a trailing joiner shapes the letter before it in a script that joins ([validated by: leaves a joiner the user typed where no cut reached it, since it shapes the letter before it](../../src/infrastructure/stores/sessionPreview.test.ts#L94)).
- A label is therefore a fixed point of the rule that produced it, which is what lets the transport re-apply the rule to a store's answer without changing a label the store already cut ([validated by: is a fixed point, so a label put through again is the label the store already answered with](../../src/infrastructure/stores/sessionPreview.test.ts#L74)).
- That bound is the stores' own, exported as one function rather than reimplemented at the boundary, so the wire and a store cannot disagree about what a label is ([validated by: holds text a store answered with to the same bound, however long it is and whatever type it is](../../src/infrastructure/stores/sessionPreview.test.ts#L106)).
- A label asked for on a server that serves no list at all is inert, and warned about at startup rather than left silent; that line is also what shows every field of `transport.history` reaching the transport rather than only the switch the engine reads first ([validated by: forwards every field of transport.history, not only the switch the engine reads first](../../src/config.test.ts#L312)).
- The strip is on the way out and not merely in what was asked for, so a store that volunteers a preview to a deployment that did not turn previews on still puts none on the wire ([validated by: strips a preview the store volunteered when this deployment did not turn previews on](../../src/transport/conversationList.test.ts#L137)).
- A client that names a `?sessionId=` the server will ignore, because resume is off, is reported rather than passed over in silence, since the client is handed a new session with nothing said ([validated by: warns when a client names a session id that resume being off makes the server ignore](../../src/transport/conversationList.test.ts#L247)).
- It is reported once per engine, not once per upgrade, since the line is a deployment fault and a per-upgrade one could be flooded by any client; a second engine in the same process still reports its own ([validated by: warns once per engine, so a second engine in the same process reports its own ignored id](../../src/transport/conversationList.test.ts#L289)).
- A list is worth nothing to a client unless `transport.resume` is on too, since `?sessionId=` is read only under resume: the engine warns at startup for history without it, and the docs say so where they tell a client to reconnect with a row's id ([validated by: warns at startup when history is on without resume, since no row could then be opened](../../src/transport/conversationList.test.ts#L236)).
- A client picks a conversation by reconnecting with `?sessionId=` from a row, which session resume already authorises and replays: there is no switch frame and no second replay path ([validated by: hands a client an id it can rejoin the conversation with](../../src/transport/conversationList.test.ts#L538)).
- One read is in flight per socket: ten frames arriving in a tick are ten answers and one query at a time, since nothing else in the transport stops a client turning frames into parallel database reads ([validated by: reads the store once at a time per socket, however many frames arrive in one tick](../../src/transport/conversationList.test.ts#L463)).
- A `list_conversations` sent while a turn is streaming is answered in the middle of it — after the turn's user entry and before the assistant entry it is still producing — because a history request is not a turn and waits on no lock ([validated by: answers a list in the middle of a streaming turn, before that turn ends](../../src/transport/conversationList.test.ts#L490)).

## When the frame cannot be answered

- Without `transport.history`, the frame is answered with an `error` of code `UNSUPPORTED` and no list ([validated by: refuses the frame when conversation history is not turned on](../../src/transport/conversationList.test.ts#L302)).
- A store implementing no `listFor` is answered with the same code, never an empty list: a client cannot tell "no conversations" from "the server could not look", and a history view is the one place that difference matters ([validated by: refuses the frame when the store cannot list, rather than reporting no conversations](../../src/transport/conversationList.test.ts#L353)).
- A handler built without a store answers the frame too, with the same `UNSUPPORTED`: a client left waiting on a frame nothing will answer is the one outcome the engine never produces ([validated by: answers a handler built with no store at all, rather than leaving the client waiting](../../src/transport/conversationList.test.ts#L340)).
- A store that throws `StoreCannotList` is answered `UNSUPPORTED` rather than `SERVER_ERROR`, and logged by that name, so a collection injected without a `find` reads as the misconfiguration it is rather than as a database that failed ([validated by: tells a store that cannot list apart from one that failed, so a misconfiguration is not a blip](../../src/transport/conversationList.test.ts#L365)).
- Only the read and the mapping of what it answered are attributed to the store: a send that throws is reported as handling the message, not as the store having failed, and the next list on that socket is still answered ([validated by: blames a send that threw on the socket, not the store, and still answers the next list](../../src/transport/conversationList.test.ts#L434)).
- A store that fails is answered `SERVER_ERROR` with none of the store's own words, the socket stays open, and the log carries the session id, the user id and the error's type rather than its message, since a driver's message can hold a connection string and its password ([validated by: answers a failing store with a server error, keeps the socket open, and logs no word the store said](../../src/transport/conversationList.test.ts#L388)).

- A store that rejects with something that is not an `Error` is logged by that value's type, so a driver throwing a string is still described ([validated by: reports the type of a rejection that is not an Error, rather than failing to describe it](../../src/transport/conversationList.test.ts#L418)).

## Reading the frame

- A `list_conversations` naming no window is accepted, and a field the frame does not define — a `userId`, for one — is dropped rather than forwarded ([validated by: accepts list_conversations with no window, and keeps no field the frame does not define](../../src/transport/ws/validation.test.ts#L23)).
- `limit` is accepted as a whole number from 1 to 200, the bound the store caps a page at ([validated by: accepts a whole-number limit inside the page bound and a cursor carrying both halves](../../src/transport/ws/validation.test.ts#L29)).
- Anything else is refused rather than clamped, with an error naming `limit`, since a limit of `0`, `201`, `1.5`, `'10'` or `NaN` is a client bug worth reporting ([validated by: refuses a limit that is not a whole number from one to two hundred, naming the field](../../src/transport/ws/validation.test.ts#L37)).
- `before` is accepted only carrying both halves, an ISO `updatedAt` and a `sessionId` of the shape the upgrade reads one in, and is refused with an error naming `before`: a cursor missing its id would page on a time alone and skip a conversation on a tie ([validated by: refuses a cursor missing either half, or carrying a time nothing can parse, naming the field](../../src/transport/ws/validation.test.ts#L48)).
- The validator dispatches through a `Map` rather than an object literal, so a frame whose `type` names an inherited member — `constructor`, `__proto__`, `toString` — reads as an unknown type; the `switch` the table replaced was equally safe, an object keyed by the frame's own `type` would not have been ([validated by: answers a frame naming an inherited member as an unknown type, rather than reaching it](../../src/transport/ws/validation.test.ts#L66)).

## A cursor the caller can actually hold

- A cursor's `updatedAt` may be a `Date`, an ISO string or an epoch number, so a summary that went through JSON on its way to a client and back still pages ([validated by: pages on a cursor that has been through JSON, and refuses one carrying no usable moment](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L123)).
- `MongoSessionStore` reads such a cursor as a date before it queries, since a string compares against no stored BSON date and would quietly match none of them ([validated by: pages on a cursor that has been through JSON, where a string would have matched no stored date](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L306)).
- A cursor carrying no usable moment is refused with an error naming it, rather than read as no cursor at all, which would answer the first page again and repeat rows a client has already shown ([validated by: pages on a cursor that has been through JSON, and refuses one carrying no usable moment](../../src/infrastructure/stores/inMemoryConversationList.test.ts#L123)).

## A collection that cannot list

- `find` is optional on `CollectionLike`, so an adapter written before conversation lists existed still satisfies the port ([validated by: refuses to list on a collection that implements no find, rather than reporting no conversations](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L331)).
- A store built on a collection without it refuses to list, rather than reporting that the user has no conversations ([validated by: refuses to list on a collection that implements no find, rather than reporting no conversations](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L331)).

## When the store cannot answer

- A store whose collection fails rejects rather than answering a partial or empty list: what to show a user who may have conversations is the caller's decision, and an empty history is not a safe guess ([validated by: rejects rather than answering a partial list when the collection fails](../../src/infrastructure/stores/mongo/mongoConversationList.test.ts#L381)).
