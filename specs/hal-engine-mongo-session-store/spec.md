# MongoDB Session Store

| Field  | Value                |
| ------ | -------------------- |
| Issue  | re-cinq/HALEngine#92 |
| Status | Implemented          |

The engine shipped `InMemorySessionStore` and nothing else, so a conversation died with the process. That is not only a resume problem: a conversation that cannot outlive its socket cannot have a retention period applied to it, cannot be handed to a human on escalation, and cannot be replayed when a customer disputes what the agent told them. In a support deployment its content is the customer's own booking data. Every consumer that needed durability wrote the same workaround, because the interface offered no write signal and its `delete` meant eviction to the engine and erasure to a database; the worked example was a consumer's own `MongoSessionStore`, a cache over an in-process `Map` with three private methods doing the real work. Shipping one store here is what stops a third consumer writing a fourth variant. **This issue does not deliver conversation resume, and this store does not make the engine safe to run as more than one instance against one conversation.**

## The collection is the truth

- A session written by `save` is returned by `get` in a second store built on the same collection, so the cache is an optimisation rather than the record ([validated by: is returned by a second store built on the same collection](../../src/infrastructure/stores/mongo/mongoDurability.test.ts#L12)).
- `delete` is the consumer's erasure primitive and the engine never calls it, so here it removes the document rather than only the cache entry; a later `get` finds nothing ([validated by: erases the document when the consumer calls delete](../../src/infrastructure/stores/mongo/mongoDurability.test.ts#L24)).
- `clear` empties the cache alone, and every document survives it ([validated by: empties the cache on clear while every document survives](../../src/infrastructure/stores/mongo/mongoDurability.test.ts#L104)).
- The cache in front of the collection is bounded by `maxAgeMs`, eight hours by default as in `InMemorySessionStore`: a stale entry is dropped when it is read — whether or not its document is still there — and swept when another session is cached even if nobody reads it again, and dropping one erases nothing because the next `get` reloads it from the collection ([validated by: sweeps a session nobody reads again when another is cached](../../src/infrastructure/stores/mongo/mongoCacheBound.test.ts#L53), [validated by: drops a stale entry and reloads it, leaving the document untouched](../../src/infrastructure/stores/mongo/mongoCacheBound.test.ts#L36)).
- `evict` removes the document as well as the cache entry: the engine calls it only for a session whose socket closed before the client received it, so its document holds no entries and leaving one behind would accumulate conversations nobody can read ([validated by: leaves no document behind when a session the client never received is evicted](../../src/infrastructure/stores/mongo/mongoDurability.test.ts#L113)).
- `count` reports documents rather than cache entries, so it falls when a document is erased and is unmoved by a cache-only `clear` ([validated by: empties the cache on clear while every document survives](../../src/infrastructure/stores/mongo/mongoDurability.test.ts#L104)).
- `get` reports `undefined` for a session no collection holds ([validated by: returns undefined for a session no collection holds](../../src/infrastructure/stores/mongo/mongoDurability.test.ts#L130)).
- `create` returns the session with the `authHeaders` and `workspaceId` it was given, which live in memory for the tools and are never written ([validated by: carries the create options onto the session it returns](../../src/infrastructure/stores/mongo/mongoDurability.test.ts#L136)).
- A `create` whose write fails caches nothing: the rejection reaches the caller and the store keeps no session it never stored, so a database outage cannot fill memory with conversations — or with the credentials they carry ([validated by: keeps nothing in the cache, so a failing database cannot fill memory](../../src/infrastructure/stores/mongo/mongoWriteFailure.test.ts#L18)).
- A `save` that receives no acknowledgement from the driver — as a collection returning `undefined` rather than a match object would — completes without error and without a warning, so the caller's turn is not aborted by a missing confirmation ([validated by: completes without error or warning when updateOne returns no result](../../src/infrastructure/stores/mongo/mongoWriteFailure.test.ts#L33)).
- A `save` the driver reports matched no document logs a warning that names no session, because the conversation it would name may be one an erasure request just removed ([validated by: warns without naming the session when no document matched](../../src/infrastructure/stores/mongo/mongoWriteFailure.test.ts#L42)).
- A `save` of a copy other than the cached object drops the cached one, so a caller that builds its own `ChatSession`, as the REST router does, never leaves `get` answering with what preceded its write ([validated by: POST /chats then POST /chats/:id/messages stores the chat in the session store, and after its erasure a further message writes nothing](../../src/transport/sessionErasure.acceptance.test.ts#L106)).

## Erasing, as opposed to evicting

- `eraseConversation` removes the document permanently, and a later `get` reports `undefined` ([validated by: is gone for good once eraseConversation removes it](../../src/infrastructure/stores/mongo/mongoDurability.test.ts#L39)).
- It reports `false` for a session it never held, rather than pretending to have erased one ([validated by: reports false when eraseConversation names a session it never held](../../src/infrastructure/stores/mongo/mongoDurability.test.ts#L52)).
- A `save` from a session the caller still holds writes nothing back after `eraseConversation` — the store refuses to reinsert the document, and `count` stays zero ([validated by: save after eraseConversation writes no document back](../../src/infrastructure/stores/mongo/mongoDurability.test.ts#L94), [validated by: create, eraseConversation, then save of the session a socket still holds: await store.count() is 0](../../src/transport/sessionErasure.acceptance.test.ts#L50)).
- A `save` from a session the caller still holds writes nothing back after `eraseOlderThan` removed it — no document is reinserted and `count` stays zero ([validated by: create with createdAt back-dated past a cutoff, eraseOlderThan(cutoff), then save of the held session: no document is written](../../src/transport/sessionErasure.acceptance.test.ts#L64)).
- **GDPR, Art. 17, over a live socket.** A turn, an erasure, and a second turn leaves the conversation permanently erased — the second turn's save writes nothing back, and `count` stays zero ([validated by: GDPR. Over a real socket: a turn, an erasure, a second turn, and the conversation stays erased](../../src/transport/sessionErasure.acceptance.test.ts#L80)).
- A live session created after the cutoff is the same cached object before and after `eraseOlderThan`, because the eviction touches only what it deleted ([validated by: A live session created after the cutoff is the same object from get before and after eraseOlderThan](../../src/transport/sessionErasure.acceptance.test.ts#L146)).
- An `eraseOlderThan` whose delete rejects still drops the sessions it targeted from the cache, because a write-concern timeout can follow a delete the server applied, while every live session it never targeted keeps its one cached object ([validated by: An eraseOlderThan whose delete applies and then rejects drops the sessions it targeted and keeps every other cached session](../../src/transport/sessionErasure.acceptance.test.ts#L158)).
- A `get` racing an `eraseConversation` of the same id never re-caches the erased session: the erasure withdraws every read still waiting on the collection, and a withdrawn read returns what it read without caching it ([validated by: A get racing an erasure of the same id never leaves the erased session cached](../../src/transport/sessionErasure.acceptance.test.ts#L180)).
- The withdrawal happens once the delete resolves, so a `get` that began while the delete was still pending and is still waiting when it resolves is withdrawn ([validated by: withdraws a read begun while the delete was pending and still waiting when the delete resolved](../../src/infrastructure/stores/mongo/mongoEraseRace.test.ts#L77)).
- A `get` that began while the delete was pending and finished before it resolved is dropped from the cache once it does ([validated by: drops a read begun while the delete was pending that finished before the delete resolved](../../src/infrastructure/stores/mongo/mongoEraseRace.test.ts#L81)).
- `eraseAll` withdraws every pending read too, so a `get` waiting on the collection when it ran caches nothing ([validated by: never re-caches a session eraseAll removed while the read was waiting](../../src/infrastructure/stores/mongo/mongoEraseRace.test.ts#L60)).
- An erasure withdraws only the reads of the ids it erased, so a read of another session still caches what it finds ([validated by: leaves a pending read of another session to cache what it finds](../../src/infrastructure/stores/mongo/mongoEraseRace.test.ts#L100)).
- An erasure keeps no record of the ids it removed once it completes, so a later read of an erased id caches what it finds and the memory the store holds is bounded by the reads in flight, not by every erasure the process has made ([validated by: lets a later read cache an id it erased, so it keeps no record of erasures](../../src/infrastructure/stores/mongo/mongoEraseRace.test.ts#L112)).
- An `eraseConversation` whose delete rejects still drops the conversation from the cache, because the rejection may follow a delete the database applied, and dropping a cache entry erases nothing ([validated by: still drops the conversation from the cache on eraseConversation, since the delete may have landed](../../src/infrastructure/stores/mongo/mongoEraseRace.test.ts#L141)).
- An `eraseAll` whose delete rejects still empties the cache, for the same reason ([validated by: still empties the cache on eraseAll, since some documents may have gone](../../src/infrastructure/stores/mongo/mongoEraseRace.test.ts#L145)).
- `eraseOlderThan(cutoff)` removes every document this store wrote whose `createdAt` precedes the cutoff, and no others, asserted at the boundary with one document a second either side ([validated by: erases only what was created strictly before the cutoff](../../src/infrastructure/stores/mongo/mongoDurability.test.ts#L58)).
- It reads string ids alone, the only ids this store writes, so a full page of documents another tool wrote under a different `_id` type cannot end the sweep early, and those documents are left alone ([validated by: sweeps every string id past a full page of foreign ids, and leaves the foreign documents alone](../../src/infrastructure/stores/mongo/mongoEraseOlderThan.test.ts#L143)).
- Each page is read along the `_id` index by hint, so the walk is one pass whatever indexes an operator adds ([validated by: pages string ids along the _id index, so neither a foreign id type nor an added index changes the walk](../../src/infrastructure/stores/mongo/mongoEraseOlderThan.test.ts#L45)).
- `eraseOlderThan` evicts only the sessions it deleted from the cache, leaving any live session it never touched still cached and reachable by the same object reference ([validated by: evicts only the sessions it deleted, leaving live ones in cache](../../src/infrastructure/stores/mongo/mongoEraseOlderThan.test.ts#L26)).
- Each session `eraseOlderThan` deleted leaves the cache with it ([validated by: evicts the sessions it deleted from the cache](../../src/infrastructure/stores/mongo/mongoEraseOlderThan.test.ts#L36)).
- `eraseOlderThan` deletes the ids it read rather than re-applying the date filter, so a session created between the read and the delete is neither deleted nor left cached without its document ([validated by: deletes exactly the ids it read, so what it deletes and what it evicts agree](../../src/infrastructure/stores/mongo/mongoEraseOlderThan.test.ts#L64), [validated by: leaves a session created between its read and its delete both stored and cached](../../src/infrastructure/stores/mongo/mongoEraseOlderThan.test.ts#L170)).
- It reads and deletes in pages of a thousand ids, so no single command can outgrow MongoDB's 16 MiB limit however large the backlog ([validated by: deletes a backlog in batches of a thousand ids, so no single command can outgrow the size limit](../../src/infrastructure/stores/mongo/mongoEraseOlderThan.test.ts#L97)).
- Each page is read past the last id of the one before, so documents a delete leaves behind cannot hold the sweep in a loop ([validated by: reads each page past the last id, so documents a delete leaves behind cannot hold the sweep in a loop](../../src/infrastructure/stores/mongo/mongoEraseOlderThan.test.ts#L126)).
- A read begun while a page was being deleted and still waiting when the delete resolved is withdrawn, as it is for `eraseConversation` ([validated by: withdraws a read begun while an eraseOlderThan batch was deleting and still waiting when it resolved](../../src/infrastructure/stores/mongo/mongoEraseRace.test.ts#L95)).
- On a collection that implements no `find` it cannot learn which ids go, so it rejects with `StoreCannotList` before deleting anything and leaves every cached session where it was, rather than emptying the cache on every retry ([validated by: refuses with StoreCannotList, deleting nothing and keeping every cached session](../../src/infrastructure/stores/mongo/mongoEraseOlderThan.test.ts#L77)).
- `eraseAll` removes every document this store can see ([validated by: erases every conversation on eraseAll](../../src/infrastructure/stores/mongo/mongoDurability.test.ts#L122)).
- **GDPR erasure, Art. 17.** `eraseConversation` is the method an erasure request calls for, and `delete` is its synonym for a consumer holding only the `SessionStore` interface; `docs/session-stores.md` opens with the table saying which member erases and which only evicts, because `clear` still does not ([validated by: is gone for good once eraseConversation removes it](../../src/infrastructure/stores/mongo/mongoDurability.test.ts#L39)).

## Retention needs whole-conversation timestamps

- Each document carries `createdAt` and `updatedAt`, so a retention period is expressible without a timestamp on every entry. A second `save` advances `updatedAt` and leaves `createdAt` where `create` set it, because `save` updates `updatedAt` in place and never touches `createdAt` — there is no read-modify-write for a concurrent save to lose ([validated by: advances updatedAt on a second save while createdAt stays where it was](../../src/infrastructure/stores/mongo/mongoDurability.test.ts#L74)).
- The clock is injectable, because `Date` has millisecond resolution and two saves inside one millisecond would otherwise produce an `updatedAt` that had not moved ([validated by: advances updatedAt on a second save while createdAt stays where it was](../../src/infrastructure/stores/mongo/mongoDurability.test.ts#L74)).

## What is never written

- **GDPR data minimisation, Art. 5(1)(c).** No persisted document holds an `authHeaders`, `authorization`, `cookie` or `host` key at any depth, asserted by walking every key of the serialised document rather than checking its top-level fields — depth is the point rather than a flourish, since `ToolEntry.toolInput` is model-supplied data and a token can arrive nested inside a tool's input, so stripping only the top level would be theatre ([validated by: holds no credential key at any depth of the stored document](../../src/infrastructure/stores/mongo/mongoRedaction.test.ts#L50)).
- The redaction removes credentials and nothing else, so the guarantee is not met by writing an empty document ([validated by: keeps everything that is not a credential, so the redaction is not simply emptying the document](../../src/infrastructure/stores/mongo/mongoRedaction.test.ts#L57)).
- Sanitising copies rather than mutates, because the live session keeps the credentials the orchestrator hands to tools through `ToolContext` ([validated by: leaves the caller their in-memory credentials, which the tools still need](../../src/infrastructure/stores/mongo/mongoRedaction.test.ts#L66); a conversation reloaded in a fresh process therefore has no `authHeaders`, and a tool that reads them sees nothing until the caller re-authenticates, which is the intended trade-off and matches what the transport already does on socket close).

## The connection is the consumer's

- The store takes a collection, a client with a database name, or a URL with one; nothing in `src/` reads the environment or carries a default host ([validated by: connects from a url the consumer supplied, and closes the client it opened](../../src/infrastructure/stores/mongo/mongoConnection.test.ts#L19)).
- `close` closes only a client the store opened, so a client the consumer owns stays open and usable afterwards ([validated by: uses a client the consumer owns and leaves it open](../../src/infrastructure/stores/mongo/mongoConnection.test.ts#L29)).
- The collection name defaults when the consumer names none ([validated by: defaults the collection name when the consumer names none](../../src/infrastructure/stores/mongo/mongoConnection.test.ts#L46)).
- `createMongoSessionStore` builds the same store from the same options, matching how the providers are exported ([validated by: is built by the factory the package exports, on the same options](../../src/infrastructure/stores/mongo/mongoConnection.test.ts#L58)).

## Costing nobody else the driver

- `mongodb` is an optional peer dependency mirrored into `devDependencies`, exactly as the two provider SDKs are, and a consumer with none of the optional peers installed can still import the package root and construct the in-memory store ([validated by: can import the package root and use the in-memory store](../../src/infrastructure/stores/mongo/optionalPeers.test.ts#L20)).

## Rationale

The driver is reached through `await import('mongodb')` inside the connect path rather than a top-level import, which the widened `Awaitable` interface makes possible without an asynchronous factory. The optional-peer check runs the built package in a child process with the three optional peers made unresolvable, because ts-jest erases a type-only import either way and an in-process assertion would prove nothing. The exported option types are structural ports rather than the driver's own, so `mongodb` appears nowhere in the published declarations and a consumer without the driver installed can still type-check against the package.

The cache is load-bearing rather than an optimisation of convenience: the orchestrator mutates a session in place while a turn streams, so `get` has to hand back a stable object for the same id. The consequence is that two store instances in one process are not coherent with each other until a `save`, and two processes serving one conversation at once is not something this store supports.

## Out of scope

Conversation resume from a session id (re-cinq/HALEngine#45); telling an expired session from one that never existed (re-cinq/HALEngine#46); bounding and redacting what a session keeps (re-cinq/HALEngine#41); the retention period itself, which is a deployment's decision and belongs in the consumer's configuration with a named human behind it; and any scheduler — `eraseOlderThan` is a method the consumer calls, because a library-owned timer keeps a consumer's process alive.
